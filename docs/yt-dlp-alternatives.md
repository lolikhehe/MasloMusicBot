# yt-dlp vs альтернативи: чи можна «не оновлюватись»? (2026-11-16, гілка experimental)

**Коротка відповідь: ні.** YouTube змінює внутрішні механізми ~кожні 2–3 тижні,
і будь-який завантажувач ламається однаково. Єдиний вибір — хто робить
оновлення: ми вручну, чи сам рушій автоматично. Рішення на гілці experimental —
друге (автооновлення yt-dlp при старті контейнера), плюс цей звіт.

## Що реалізовано на гілці experimental

`docker/entrypoint.sh` (ENTRYPOINT тини → entrypoint → `music-bot`):

1. Рахує `GET https://api.github.com/repos/yt-dlp/yt-dlp/releases/latest` (unauthenticated, 1 запит на старт).
2. Якщо latest == pinned (зараз 2026.10.26) — нічого не качає, працює pinned.
3. Якщо latest новіший — качає `yt-dlp_linux` зі сторінки релізу у `/data/tmp/bin/yt-dlp` (rootfs read-only, писати можна тільки у volume), перевіряє `--version` == tag, виставляє `YTDLP_PATH` перед стартом бота.
4. Будь-який збій (нема мережі, GitHub ліміт, пошкоджений файл) → лог + старт на pinned binary. Бот ніколи не залежить від мережі при старті.
5. `YTDLP_AUTO_UPDATE=false` повністю вимикає. `tini`-ланцюг не змінюється; скрипт — POSIX sh, `.gitattributes` фіксує LF.

Обмеження з чесності: автооновлення спрацьовує **при (ре)старті контейнера**, а
не в фоновому режимі — довгоживучий контейнер сам не оновиться. Тому потрібен
регулярний рестарт (наприклад, щотижневий `docker compose up -d --force-recreate
bot` у cron/планувальнику хоста; тоді оновлення повністю руки не торкаються).

## Живий тест cobalt (self-hosted, 2026-11-16)

- `ghcr.io/imputnet/cobalt:latest` = 11.7.1, піднятий локально на 127.0.0.1:17010.
- `POST / {"url": "https://www.youtube.com/watch?v=Gi5g7gJbwxQ", "downloadMode": "audio"}`
  → `{"status":"tunnel","filename":"First Fragment - In'el - Unique Leader Records.mp3"}` — знайшов саме той альбомний трек, що раніше ловив 403.
- `GET tunnel` для «Me at the zoo» (jNQXAC9IVRw) → файл 309 288 байт, завантажився повністю.
- Тобто рушій **працює сьогодні**. Але:
  - **немає пошуку** — cobalt бере URL, а весь потік бота (`/` текст → `ytsearch1:` → найкращий збіг) зав'язаний на пошуку; довелося б писати свій InnerTube-пошук, який ламається тим самим чином;
  - hosted-інстанси для ботів без дозволу власника — не можна (документація cobalt), тож self-host — ще один сервіс на утриманні;
  - cadence комітів гірша за yt-dlp; це не «без оновлень», це «повільніше отримуємо фікси»;
  - плюс окрема служба, порт, оновлення образу — замість одного бінарника в образі.

## Вердикт

Замінити yt-dlp на «щось стабільніше, що не треба оновлювати» **неможливо** —
для YouTube такого не існує в принципі. Реалістично:

1. **Зроблено (experimental):** автооновлення yt-dlp при старті + регулярний рестарт → ручні оновлення зникають повністю.
2. **Не робити:** переходити на rusty_ytdl/NewPipeExtractor/cobalt «заради стабільності» — отримуємо гірший каденс фіксів і/або зайву інфраструктуру без жодного виграшу.
3. **Можливе майбутнє (не зараз):** cobalt як *додатковий* fallback-рушій для прямих YouTube-URL (не для пошуку), якщо yt-dlp якийсь день довго не працюватиме — за потреби окреме рішення.
4. **Неминуче:** навіть із автооновленням можливі періоди повної непрацездатності YouTube-розпізнавання на 1–3 дні (до виходу фікса) — тоді врятовує SoundCloud/Bandcamp fallback, який уже в боті.

Якщо все влаштовує — зливати experimental у main окремим комітом після тесту тижнем.
