# Порівняння з Python-ботами (чесно, без вигаданих цифр)

Цей документ порівнює **цю реалізацію** (Rust, teloxide, Postgres) із **типовим
Python-музичним ботом** (aiogram / python-telegram-bot + yt-dlp + SQLite/Redis).
У репозиторії **немає вихідного коду Python-бота**, тому це порівняння
архітектурне, а не результат head-to-head бенчмарку. Там, де немає заміру,
прямо написано **NOT MEASURED** — жодних «у 5 разів швидше».

## Спільна правда (важливіше за мову)

- Обидва варіанти зазвичай кличуть **yt-dlp** — це PyInstaller-пакет на Python.
  Наш `Dockerfile` досі його завантажує й використовує. Тому **холодне
  завантаження домінується не мовою бота, а мережею до джерела та завантаженням
  файлу в Telegram**. Rust не робить YouTube швидшим.
- Обидва можуть працювати з Postgres, webhook і кількома репліками. Різниця —
  **яка реалізація вже є в цьому репо**, а не обмеження Python.
- Кінцева затримка «до музики в плеєрі» включає Telegram API, який ми не
  контролюємо. S1–S4 лишаються **NOT MEASURED** для обох.

## Порівняльна таблиця (архітектура, не швидкість)

| Вісь | Цей Rust-бот | Типовий Python-бот |
|---|---|---|
| Паралелізм | tokio, багатопотоковий рантайм без GIL | asyncio зазвичай один потік на процес; CPU-робота блокує event loop без окремих процесів |
| Типобезпека SQL | `sqlx::query!` + `.sqlx`, перевірка на компіляції | рядки SQL, помилки знаходяться в рантаймі (або в ORM) |
| Спільний стан | selections/rate limits/search cache в Postgres | часто in-memory або окремий Redis |
| Статичний бінар | один `music-bot`, `lto=fat`, mimalloc | потрібні Python + venv + залежності в образі |
| Cold path | yt-dlp (Python) як зовнішній процес | yt-dlp як бібліотека/процес — **та сама вартість** |
| PNG-чарти | чистий Rust (`image` + `ab_glyph`, шрифт у бінарі) | Pillow/matplotlib (важчий image-стек) |
| Спостережуваність | `/metrics` Prometheus + ALERTS, k6-стенд на 3 репліки | залежить від того, чи додав автор метрики |
| Швидкість розробки | повільніше (компіляція, типи, ручна робота з SQL) | **швидше** — величезна екосистема, прості прототипи |
| Поріг входу | вищий (Rust, sqlx offline, tokio) | нижчий — aiogram добре задокументований |

## Де Rust тут реально виграє (структурно, без цифр)

1. **Немає GIL.** Рендер колажів іде через `spawn_blocking`, HTTP-клієнти
   спільні з keep-alive, фонові таски (janitor, дайджести) — окремі tokio-задачі.
   Python-боту для того самого доводиться явно виносити CPU в процеси.
2. **Один бінар на деплой.** `Dockerfile` + cargo-chef, `SQLX_OFFLINE=true`,
   немає venv/pip у runtime. (Але yt-dlp усередині — PyInstaller, тож Python
   у образі формально присутній.)
3. **Компіляційна перевірка SQL.** Міграції + `query!` ловлять розсинхрон схеми
   ще на CI; у Python це зазвичай знаходить перший запит у проді.
4. **Подільний стан без Redis.** Rate limits і selections лежать у Postgres,
   тому webhook-репліки й load-стенд працюють без додаткового сервісу.

## Де Python був би кращим

- Якби головною метою була **швидкість ітерацій** і не планувався
  багаторепліковий деплой — aiogram-бот був би простішим і дешевшим у підтримці.
- Екосистема готових рішень для Telegram (файлові менеджери, FSM, адмінки) у
  Python значно багатша.
- Якщо був би готовий Python-бот із тими самими Postgres/webhook/метриками —
  різниця в latency була б значно меншою, ніж різниця в мові.

## Висновок

Цей проєкт виграв не «швидше за Python», а **керованістю**: спільний стан,
перевірена схема, передбачувані фонові задачі й відтворюваний деплой. Cold-path
виграшу від мови майже немає — він однаково залежить від yt-dlp і Telegram.
Для чесного порівняння потрібно запустити еквівалентного Python-бота на тому
самому хості, з тим самим Postgres і тим самим mock API, зняти ті самі
гістограми — тоді S1–S4 перестануть бути NOT MEASURED.
